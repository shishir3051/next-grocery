# Audit Findings — Full Appendix

Generated 2026-11-02 by a multi-agent audit: six auditors, each one checked by an adversarial verifier, plus a completeness critic. Different auditors sometimes found the same issue, so there are duplicates. The prioritized, de-duplicated plan is in [IMPROVEMENT_PLAN.md](IMPROVEMENT_PLAN.md).

Verdict key: **confirmed** means re-checked in the code; **partially-correct** means the issue is real but some detail (line, scope or severity) was corrected by the verifier (see the note); **critic-verified** means found and checked in the critic pass.


## Security & Auth (18)

### [CRITICAL] Any logged-in user can make themselves admin via GET /api/admin/setup
- **Where:** [src/app/api/admin/setup/route.ts:18](../src/app/api/admin/setup/route.ts#L18)
- **Verdict:** confirmed · **Effort:** S
- **Evidence:** The route only checks that a session exists (`if (!session || !session.user)` at L13), then runs `User.findOneAndUpdate({ email: session.user.email }, { role: "admin" }, { new: true })` (L18-22). There is no role check, setup token, 'first user only' rule or environment gate. The file calls itself a "Temporary setup route" (L8).
- **Impact:** Anyone can register and verify an email, then open /api/admin/setup and get full admin rights over products, orders (customer names, addresses and phones), users, coupons, settings and news. Every other admin protection in the app depends on this route not existing. The admin panel then loads right away, because admin routes look up the role in the DB.
- **Fix:** Delete this route. To bootstrap the first admin, use a one-off CLI script that calls promoteUserToAdmin (src/lib/promoteAdmin.ts) with MONGODB_URI from the environment, and keep that helper out of any API route. If an HTTP bootstrap is really needed, allow it only when `await User.countDocuments({ role: 'admin' }) === 0`, require a secret header matched against an env var, and accept POST only.
- **Verifier note:** Verified in src/app/api/admin/setup/route.ts L10-22: a GET handler that only checks for a session and then sets role:'admin' on the caller's email. There is no role, token, first-admin or env gate, and no middleware/proxy exists. One nuance: the JWT role is only set at sign-in (auth.ts L51-53), so routes that trust the token role (hero, news/admin) start working only after the user logs in again. Routes that look up the role in the DB (products, orders, users, coupons, settings) work right away. The fix is correct.

### [CRITICAL] SSLCommerz callback trusts client-supplied status, so anyone can mark an order paid
- **Where:** [src/app/api/payments/ssl-status/route.ts:19](../src/app/api/payments/ssl-status/route.ts#L19)
- **Verdict:** confirmed · **Effort:** M
- **Evidence:** The route has no authentication and no signature or validation call. `const orderId = searchParams.get('orderId')` (L10) and `const ssl_status = formData.get('status')` (L15) come straight from the request, then `if (status === 'success' && ssl_status === 'VALID') { const order = await Order.findById(orderId); ... order.paymentStatus = 'paid'; order.status = 'processing'; await order.save(); }` (L19-34). `tran_id` is read (L14) but never compared with `order.paymentProviderId`. The amount is never checked and the `val_id` is never validated with SSLCommerz's validator API. IPN (`status=ipn`) is ignored.
- **Impact:** An attacker starts an SSLCommerz checkout (which creates a provisional order and returns its id in the success_url) and abandons it. They then run `curl -X POST '/api/payments/ssl-status?status=success&orderId=<id>' -d 'status=VALID'`. The order becomes paid/processing with no money taken, and goods ship for free. Stock is also decremented on every forged call for any unpaid order id.
- **Fix:** Treat the browser redirect as untrusted. Take `val_id` from the POST body and call SSLCommerz's validation endpoint (`/validator/api/validationserverAPI.php?val_id=...&store_id=...&store_passwd=...`) on the server. Mark the order paid only when the response has status VALID/VALIDATED, `tran_id === order.paymentProviderId`, and `amount`/`currency` match `order.totalAmount`/BDT. Do this inside an atomic `Order.findOneAndUpdate({ _id, paymentStatus: 'unpaid', paymentProviderId: tran_id }, ...)`. Handle the IPN the same way and make the redirect handler only read state.
- **Verifier note:** Verified in ssl-status/route.ts L8-34: no auth, no val_id validation, tran_id read at L14 but never compared, amount never checked, IPN (status=ipn, no orderId) does nothing. The attacker can get their own order id from GET /api/orders (L133), so the success_url leak is not needed. Correction: stock is decremented once per unpaid order, not on every call, because the order is then marked paid. Any unpaid order works, including COD orders whose stock was already decremented in /api/orders, which leads to a double decrement. The fix (validator API, compare tran_id and amount, atomic findOneAndUpdate on paymentStatus:'unpaid') is correct.

### [CRITICAL] Unvalidated item quantity lets users create negative totals, mint wallet credit and inflate stock
- **Where:** [src/app/api/orders/route.ts:43](../src/app/api/orders/route.ts#L43)
- **Verdict:** confirmed · **Effort:** M
- **Evidence:** `items` comes from the request body and is never validated. The stock check `if (!product || product.stock < item.quantity)` (L45) passes for negative quantities. `calculatedSubTotal += (product.discountPrice || product.price) * item.quantity` (L50) then goes negative. Wallet logic: `if (user.walletBalance >= calculatedTotal) { walletDeducted = calculatedTotal; ...} user.walletBalance -= walletDeducted;` (L86-93). Stock update: `$inc: { stock: -item.quantity }` (L99-101). The order stores the client's `items` as-is (L106), including client-supplied `name`/`price`/`imageData`. The schema has no `min` on quantity (src/models/Order.ts L7).
- **Impact:** A user with any wallet balance (for example the 50 BDT referral bonus) sends `items:[{productId:X, quantity:-100}]` with `useWallet:true`. calculatedTotal becomes about -9950, walletDeducted = -9950, and walletBalance grows by 9950. They then spend that credit on real COD orders with finalAmountToPay = 0. Without a wallet, mixing +N and -N items gives free goods. Stock is inflated and admin order views show attacker-controlled names and prices.
- **Fix:** Validate the body with a schema (for example zod): items must be a non-empty array of at most about 50 entries, `productId` a valid ObjectId, and `quantity` an integer from 1 to a sane maximum. Build the stored order items on the server from the Product document (name, price, image) and never from the client. Reject orders where `calculatedTotal <= 0`, and clamp the coupon discount to at most the subtotal. Add `min: 1` to OrderItemSchema.quantity and `min: 0` to walletBalance. Decrement the wallet atomically (`findOneAndUpdate({_id, walletBalance: {$gte: amt}}, {$inc: {walletBalance: -amt}})`) and stock atomically (`{_id, stock: {$gte: qty}}`), ideally in a transaction. Apply the same validation in src/app/api/payments/ssl-init/route.ts L45-53.
- **Verifier note:** Walked through orders/route.ts. L45: `stock < -100` is false, so the check passes. L50: subtotal goes negative. L75-76: fee 50, total about -9950. L85-93: walletBalance(50) >= -9950, so walletDeducted = -9950 and `walletBalance -= -9950` credits the wallet, then user.save(). L99-101: $inc stock +100. L106: client items stored as-is. Order.ts L7 quantity has no min. ssl-init L45-53 has the same flaw (totalAmount can go negative there too). Everything is as described.

### [HIGH] Unauthenticated endpoints wipe products, categories, hero slides and news
- **Where:** [src/app/api/seed/route.ts:4](../src/app/api/seed/route.ts#L4)
- **Verdict:** confirmed · **Effort:** S
- **Evidence:** `export async function POST(request) { await seed(); ... }` has no session check. seed() runs `Category.deleteMany({}); Product.deleteMany({}); HeroSlide.deleteMany({});` (src/lib/seed.ts L167-169) and then makes one outbound fetch per product to loremflickr. `GET /api/news/seed` runs `News.deleteMany({})` (src/app/api/news/seed/route.ts L10). `GET /api/admin/restore-news` runs `News.deleteMany({})` and also `delete mongoose.models.News` (src/app/api/admin/restore-news/route.ts L40-47), with no auth even though it sits under /admin. HomeClient.tsx L157 POSTs /api/seed. /api/seed is POST-only, so prefetch or img triggers apply only to the two news GET routes, as the finding says. Severity is right: unauthenticated wiping of the whole catalog.

### [HIGH] OTP verification has no attempt limit, uses Math.random, and accepts query-object email (account takeover of unverified emails)
- **Where:** [src/app/api/auth/verify-otp/route.ts:34](../src/app/api/auth/verify-otp/route.ts#L34)
- **Verdict:** partially-correct · **Effort:** M
- **Evidence:** OTP generation: `Math.floor(100000 + Math.random() * 900000)` (src/app/api/auth/register/route.ts L23), which is not a CSPRNG. Verification: `User.findOne({ email })` with `email` taken unsanitized from JSON (L18), then `if (user.verificationOtp !== otp)` (L34). There is no failed-attempt counter, no lockout, the OTP is not invalidated on failure, and no rate limit exists anywhere. register overwrites an unverified user's password and issues a fresh OTP on every call (register L35-37) without throttling.
- **Impact:** An attacker registers victim@example.com with their own password, or re-registers over a victim's pending signup and so overwrites the victim's password. They then brute-force the 6-digit code (900k possibilities, 10-minute window, unlimited tries, renewable through register). The result is a verified account on an email they do not own, which also collects referral wallet credit. Because Mongoose does not sanitize filters, `{"email":{"$regex":"."}}` lets the attacker target any unverified user without knowing the address. Unlimited register calls also turn the app's Gmail account into an email-bombing relay.
- **Fix:** Generate the OTP with `crypto.randomInt(0, 1_000_000).toString().padStart(6,'0')`, store only its hash, and compare with `crypto.timingSafeEqual`. Add `otpAttempts` to the User model, clear the OTP after 5 failures, and enforce a resend cooldown (for example 60 s, at most 5 per hour). Do not overwrite an existing unverified user's password on re-register; only resend the OTP. Require `typeof email === 'string' && typeof otp === 'string'`, or enable `mongoose.set('sanitizeFilter', true)` globally in src/lib/mongodb.ts. Add IP- and email-keyed rate limiting to register and verify-otp.
- **Verifier note:** Core is verified: register.ts L23 uses Math.random, verify-otp L18 does findOne({email}) with an unsanitized value, L34 has no attempt counter, and the OTP is not cleared on failure. register L35-37 overwrites an unverified user's password and OTP with no throttle. verify-otp does no bcrypt work, so brute-forcing is cheap. Overstated part: `{email:{$regex:'.'}}` returns only the first matching user, which is likely a verified one and gets 'already verified'. To target unverified users the attacker has to enumerate with prefix regexes, using the distinct 'User not found'/'already verified'/'Invalid OTP' responses as an oracle. That is feasible, but not 'any unverified user without knowing the address' in one step. Predicting Math.random here is theoretical; the missing attempt limit is the real problem. The fix is correct (crypto.randomInt, hashed OTP, attempt cap, typeof checks or mongoose sanitizeFilter).

### [MEDIUM] Stored XSS: news content rendered with dangerouslySetInnerHTML and no sanitization
- **Where:** [src/app/news/[id]/page.tsx:127](../src/app/news/[id]/page.tsx#L127)
- **Verdict:** partially-correct · **Effort:** S
- **Evidence:** `dangerouslySetInnerHTML={{ __html: article.content.replace(/\n/g, '<br/>') }}`. Content is saved verbatim by POST /api/news/admin (src/app/api/news/admin/route.ts L26-36) and by PATCH, which spreads the whole body (src/app/api/news/admin/[id]/route.ts L53-58). next.config.ts sets no CSP.
- **Impact:** Any admin can publish `<img src=x onerror=...>`, and any user can become admin through /api/admin/setup. The payload runs for every visitor of the article. It can drive same-origin fetches against /api/admin/* while a real admin is browsing, for example promoting accounts, editing prices or exporting all orders and addresses through /api/admin/orders. It can also change the checkout UI.

- **Verifier note:** The sink is verified at news/[id]/page.tsx L127, with verbatim storage at news/admin/route.ts L26-36 and the PATCH body spread at news/admin/[id] L53-58. Writing requires an admin role from the JWT, so on its own this is admin-authored XSS (a malicious or compromised admin attacking visitors and other admins). The 'high' rating depends on the admin-setup escalation, which is tracked separately as critical. Standalone it is medium. The fix (render as text with whitespace-pre-line) is correct and simplest.

### [MEDIUM] SSRF: server fetches arbitrary admin-supplied URL and stores the response publicly
- **Where:** [src/lib/imageUtils.ts:109](../src/lib/imageUtils.ts#L109)
- **Verdict:** partially-correct · **Effort:** S
- **Evidence:** `const response = await fetch(url);` with no protocol, host or IP check, no size limit and no content-type check. The result is stored as `data:${contentType};base64,...`. It is called with the request's `imageUrl` in POST /api/admin/products (src/app/api/admin/products/route.ts L61-62) and saved as `imageData`, which public /api/products returns.
- **Impact:** An admin, or anyone after the /api/admin/setup escalation, sets imageUrl to `http://169.254.169.254/latest/meta-data/iam/security-credentials/...`, `http://localhost:27017` or an internal service. The server fetches it, base64-stores the body, and exposes it to anyone through /api/products, which makes this a full-read SSRF. Very large responses can also exhaust memory or blow up document size.
- **Fix:** In getBase64FromUrl, allow only `https:`, resolve the hostname and reject private, loopback and link-local ranges (or allowlist the image hosts already in next.config.ts remotePatterns). Require a `content-type` starting with `image/`, cap the body at about 2 MB with AbortController and a timeout, and set `redirect: 'error'`.
- **Verifier note:** The line number is wrong. src/lib/imageUtils.ts has 22 lines, and the fetch is at L7 (`const response = await fetch(url);`), not L109. The rest is accurate: no protocol, host, size or content-type check, called from admin/products/route.ts L61-62 and stored as imageData, which getProducts (actions.ts L38) returns in full through public /api/products. Admin is a precondition, so medium is right. The fix is correct; also cap the body size and use redirect:'manual'/'error' to stop redirect-based bypasses.

### [MEDIUM] Admin authorization is duplicated and inconsistent; JWT role is never refreshed
- **Where:** [src/lib/auth.ts:50](../src/lib/auth.ts#L50)
- **Verdict:** confirmed · **Effort:** M
- **Evidence:** The jwt callback sets `token.role = user.role` only at sign-in (L51-53) and never re-reads it. No `session.maxAge` is set, so NextAuth's 30-day default applies. src/app/api/admin/hero/route.ts L7-10 and src/app/api/news/admin/route.ts L10 / news/admin/[id] L13,L38 trust `(session.user as any).role === 'admin'` from the token. Every other admin route copies a DB lookup (`User.findOne({ email: session.user.email })` + role check) about 25 times across 9 files.
- **Impact:** A demoted or deleted admin keeps full control of hero banners and news, which are the stored-XSS sink, for up to 30 days. Deleting a user does not end their session. Orders POST still uses `session.user.id` for a deleted account. The copy-pasted checks make it easy for a new route to miss a check, as /api/admin/restore-news already does.
- **Fix:** Add a single `requireRole(...roles)` helper in src/lib (getServerSession, then `User.findById(session.user.id).select('role').lean()`), returning a 401/403 NextResponse or the user. Use it in every admin and delivery route, including hero and news. In the jwt callback, re-read role from the DB periodically (for example every 5 minutes, stored as `token.roleCheckedAt`) or on `trigger === 'update'`, and set `session.maxAge` explicitly.
- **Verifier note:** auth.ts L50-57: role is set only when `user` is present, and `trigger` is accepted but unused. No session.maxAge is set (L72-74), so the 30-day default applies. hero/route.ts L7-10 and news/admin L10, news/admin/[id] L13/L38 trust the token role. Count correction: the exact DB-lookup pattern `User.findOne({ email: session.user.email })` appears 23 times across 11 files, not about 25 across 9. The requireRole helper fix is sound.

### [MEDIUM] User input passed unescaped into MongoDB $regex (regex injection / ReDoS)
- **Where:** [src/lib/actions.ts:51](../src/lib/actions.ts#L51)
- **Verdict:** confirmed · **Effort:** S
- **Evidence:** `{ name: { $regex: searchTerm, $options: 'i' } }, { description: { $regex: searchTerm, $options: 'i' } }` (L51-52). searchTerm comes from the public `GET /api/products?search=` (src/app/api/products/route.ts L8-12) and from LLM-produced keywords in /api/ai/smart-search (L61-62). It has no length limit and no escaping.
- **Impact:** Unauthenticated requests such as `?search=(a+)+$` or `(.*a){20}` cause catastrophic backtracking on every product description in a collection scan, which ties up MongoDB CPU and works as a cheap DoS. Arbitrary regex also allows search behavior the app never intended.
- **Fix:** Escape the input with `term.replace(/[.*+?^${}()|[\]\\]/g, '\\$&')`, cap the length at about 64 characters, and require a string type. A better fix is a MongoDB text index on name and description queried with `$text`.
- **Verifier note:** actions.ts L51-52 passes searchTerm raw into $regex on name and description. It comes from public products/route.ts L8-12 with no length or type limit, and from LLM keywords in smart-search L61-62. An invalid regex only gives [] (caught), but patterns like (.*a){n} backtrack heavily on text-rich descriptions. The impact is limited by the small catalog. Escape plus a length cap, or a $text index, is the right fix.

### [MEDIUM] Unauthenticated, unthrottled Gemini endpoints with prompt injection and API-key prefix logging
- **Where:** [src/app/api/ai/smart-search/route.ts:20](../src/app/api/ai/smart-search/route.ts#L20)
- **Verdict:** confirmed · **Effort:** S
- **Evidence:** Neither /api/ai/smart-search nor /api/ai/recipes checks the session or rate-limits. Raw user text is placed into the prompt (`The user asked: "${query}"` at smart-search L27, and `${cartItems.join(', ')}` at recipes L26) with no length limit. Both log `GEMINI_KEY.substring(0, 8)` (smart-search L20, recipes L19), log the raw model output, and return `details: error?.message` to the client (L80 / recipes L65).

Minor: Gemini keys always start with 'AIza', so the 8-char prefix leaks about 4 meaningful characters. The cost-abuse risk is real.

### [MEDIUM] Coupon usageLimit not enforced at order time; fixed discounts can exceed subtotal
- **Where:** [src/app/api/orders/route.ts:56](../src/app/api/orders/route.ts#L56)
- **Verdict:** confirmed · **Effort:** M
- **Evidence:** Order creation re-validates `isActive` and `expiryDate` only (L56-60). It never checks `usageLimit` against `usedCount`, which only /api/coupons/validate checks (L39). It then does `$inc: { usedCount: 1 }` (L71). `discountFromCoupon = coupon.discountValue` for fixed coupons is not capped at the subtotal (L67). The SSL flow never increments usedCount (src/app/api/payments/ssl-init/route.ts L57-71). There is no per-user limit. /api/public/coupons returns every active coupon document to anonymous callers (src/app/api/public/coupons/route.ts L10-25).
- **Impact:** Limited-use coupons can be redeemed without limit by posting directly to /api/orders or through the SSL path. A fixed 200 BDT coupon on a cheaper basket produces a negative total, which feeds the wallet-mint bug. Coupons meant to stay private, such as staff or influencer codes, are listed publicly.
- **Fix:** Enforce the limit atomically: `Coupon.findOneAndUpdate({ code, isActive: true, expiryDate: {$gte: now}, $or: [{usageLimit: null}, {$expr: {$lt: ['$usedCount','$usageLimit']}}] }, { $inc: { usedCount: 1 } })`, and increment only after the order is committed (or after payment for SSL). Clamp with `Math.min(discount, subtotal)`. Add an `isPublic` flag and filter /api/public/coupons on it, returning only display fields. Consider a per-user redemption record.
- **Verifier note:** orders/route.ts L56-60 skips the usageLimit check, which only coupons/validate does (L39). L67 does not cap fixed discounts, and L71 increments usedCount non-atomically. ssl-init L57-71 never increments usedCount. Minor correction: public/coupons does filter out exhausted coupons (L16-21), so it returns active, unexpired, non-exhausted coupons as full documents. 'Private coupons' is speculative because there is no isPublic concept in the model. A negative total from a fixed coupon needs minOrderAmount < discountValue - deliveryFee.

### [MEDIUM] Referral reward is easy to farm and races on wallet balance
- **Where:** [src/app/api/auth/verify-otp/route.ts:55](../src/app/api/auth/verify-otp/route.ts#L55)
- **Verdict:** partially-correct · **Effort:** S
- **Evidence:** Each verification credits 50 to both the new user and the referrer (`user.walletBalance = (user.walletBalance || 0) + 50`; `referrer.walletBalance = ... + 50; await referrer.save()`, L55-63). This is a non-atomic read-modify-write. There is no cap, no self-referral or device check and no rate limit, and register accepts any email without normalization (`User.findOne({ email })`, register L19).
- **Impact:** With disposable or plus-addressed emails (user+1@gmail.com and so on, which are not normalized) an attacker farms unlimited wallet credit for one referrer, and that credit pays real orders. Concurrent verifications can also lose increments.
- **Fix:** Use `$inc` for wallet credits, cap referral rewards per referrer, normalize email (trim, lowercase) at register and login, and consider granting the reward only after the referred user's first paid or delivered order.
- **Verifier note:** Code is verified at verify-otp L55-63: non-atomic read-modify-write of +50 to both user and referrer, with no cap. Farming needs a real inbox per account (each OTP must be received), which plus-addressing or disposable mail provides. Correction to the fix: trim and lowercase do not stop plus-addressing. That needs provider-specific canonicalization or, better, delaying the reward until the referred user's first delivered order, plus a per-referrer cap. Using $inc is correct.

### [LOW] No security headers (CSP, frame-ancestors, HSTS, nosniff) configured
- **Where:** [next.config.ts:3](../next.config.ts#L3)
- **Verdict:** partially-correct · **Effort:** S
- **Evidence:** `const nextConfig: NextConfig = { images: { remotePatterns: [...] } };` has no `headers()` function, and no middleware sets them.
- **Impact:** There is no CSP to contain the news stored XSS. The admin panel and checkout can be framed, which allows clickjacking of admin actions such as role changes and deletes.
